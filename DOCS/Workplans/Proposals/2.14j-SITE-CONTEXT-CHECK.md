## (a) Every route gets the site's state through one object: met in substance

Shared by reference. Each is built once in `run.ts`:

- Config: `run.ts:172`, passed to save (`run.ts:337-343`) and publish (`run.ts:312`).
- Repo: `openedRepo`, passed to the route groups and to sync and publish (`run.ts:264`, `:309`, `:335`).
- Preview status: `createStatus` (`run.ts:198`), passed to the bundle routes (`app.ts:80`), sync (`run.ts:267`) and publish (`run.ts:317`).
- Delete guard (`run.ts:246`) and publish gate (`run.ts:204`): one each.
- Bundle source: one `BundleSource` (`run.ts:206-222`), passed as `AppDeps.bundle` (`run.ts:332`).

Two notes. Neither is changed.

1. The parsed bundle is cached in four stores, not one: `bundle-routes.ts:37`, `changes-routes.ts:72`, `overlay-routes.ts:30` and `run.ts:257` (sync and publish). Each caches by `bundleId`, so a new bundle is parsed up to four times. All four read the same source, so they agree on the current bundle at each call.
2. `bundle.json` is read from disk on every call (`bundle/source.ts:18-27`, `:40-43`). This is by design ("so a swap is seen at once"). It is per request, not per route handler.
3. Module-level state: `media/metadata.ts:42` holds a `queues` Map, reached from the upload route through `recordMedia` (`http/media.ts:80`). It is keyed by media file path, so two sites in one process cannot collide today. It is not per-site and is left as it is. If phase 3 runs two sites in one process, it moves into the per-site object with the rest of the state.

Merging the four stores would change the signatures of `registerBundleRoutes`, `registerChangeRoutes` and `registerOverlayRoutes`. `changes-routes.test.ts` and `overlay-routes.test.ts` call them, so that breaks "existing tests pass untouched". It is a phase 3 cleanup, not part of this task.

## (b) One middleware sets an `actor` that saves and publishes take the author from: missing

- No `actor` exists in `cms-server/src`.
- The author is config only: `config/schema.ts:132` (default `astroViewCMS <cms@localhost>`).
- It is written once per start into the clone's git config: `git/repo.ts:117` (`identityOf`), `:148` (`setConfig`), `:265-266` (`user.name`, `user.email`).
- Save commits with `git commit` and no author flag: `git/ops.ts:599`, reached from `save/write.ts:32` through `commitSave` (`git/ops.ts:116`).
- Publish squashes with `git commit-tree` and no author flag: `git/ops.ts:509`, reached from `sync/publish.ts:308` and `:357` through `squash` (`git/ops.ts:159`).

So save and publish take the author from the clone's git config, implicitly. Nothing on the request path names it.

## Seam size: estimated 60 to 80 lines with tests (about 48 production), not implemented

Built as the item describes (middleware sets the actor, save and publish read it, the git layer receives it), the change touches:

- `http/app.ts:30-71`: `AppDeps` field, typed Hono variables, middleware (~12 lines)
- `run.ts:328-349`: wiring (~4)
- `http/publish-routes.ts`, `http/changes-routes.ts`: pass the actor in (~8)

- `git/ops.ts`: `commitSave` and `squash`, their interfaces, and the `--author` argument (~8)
- `sync/publish.ts:302-357`: `squash` is reached through `squashCandidate` and `pushWithoutBuild`, both module-level, so the author goes through `publish`, `run` and those two (~10)
- New seam tests (~20-30)

The reason to defer is that a constant built now would be replaced in phase 3. It would change no behaviour (a constant from `git.author` writes the same author the clone config writes today), and its real value is per session, in phase 3 (`DOCS/Designs/PHASE-3-DESIGN-PROPOSAL.md:267`). The seam would be written twice.

The count is an estimate of 60 to 80 lines across 9 files. About 48 of that is production code (the list above, without the tests); the 20 to 30 test lines are the rest. Read against the workplan's "about 50 lines", production code alone is just under, so the count does not decide this. The deferral rests on the reason above.

## Decision
