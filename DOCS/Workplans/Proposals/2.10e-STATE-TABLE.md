# 2.10e state table: publish with a build check (draft for the U2 review)

Status: **approved by the user, 2026-11-18 (U2): the table and decisions D-a to D-f as recommended; the test plan changed to curated scenarios plus seeded random runs (section 5).** Written by the architect from the close plan, `sync/publish.ts` (2.10d) and the contract's error table. Nothing here is code yet. When approved it is the input of 2.10e, and 2.13b moves it into `CMS-SERVER.md`.

## 1. The decision behind it

The user chose **design 3 for phase 2** (2026-11-18): while a publish runs, saves are refused and the poll is skipped, so `cms/work` stays where it was. The editor can write again when the publish ends. The earlier plan (design 1, saves accepted during the build and re-applied after the push, settled 2026-11-13) is **deferred to phase 4 or 5**, when several editors or server drafts make a frozen editor a real cost. It is recorded in `SYSTEM-DESIGN.md` section 4 and in its "Later phases" list.

What phase 2 builds for design 1 to slot in later:

- One **publish gate** (`sync/publish-gate.ts`) is the only place that answers "may a save or a poll tick run now?" and the only place that decides what happens to saves made since the snapshot. Phase 2: it refuses them, and `afterPush` asserts that `cms/work` is still at `S`. Design 1: it accepts them, and `afterPush` re-applies them onto `C`. Routes and the poll loop call the gate and never read `status.publish.state` for this.
- The snapshot `{ candidate C, base S }` is a value that the publish passes between its steps from the first version.
- The event-order test already has the event "save during the build" and an expected answer for it. Design 1 changes that one expected answer and adds the re-apply cells.
- `409 remote-moved` and `409 publish-in-progress` are already in the contract.

## 2. The phases of a publish

`status.publish.state` stays `idle | publishing | failed`. The phases below are internal. "Locked" means the repo lock is held.

| Phase | Locked | What happens |
|---|---|---|
| `idle` | no | Gate open. `status.publish` is `idle`, or `failed` with the last error until someone acts. |
| `syncing` | yes | Gate closes. Sync with the remote. A changeset with nothing in it ends here with `200 { commit: null }`. |
| `waiting` | no | Waits (up to 120 s) for a running rebuild, as in 2.10d. |
| `validating` | yes | Delete-guard recheck, validate with the node, and the build decision (`always`, `never`, or `decideBuild` for `auto`, recomputed now). |
| `squashing` | yes | Builds the squash commit `C` with plumbing and notes `cms/work` HEAD as `S`. Releases the lock. |
| `building` | no | `C` builds in a worktree. Skipped when the decision is "no build". |
| `pushing` | yes | Takes the lock. Checks `cms/work` is still at `S`. Pushes `C`, never forced. |
| `finishing` | yes | `cms/work` resets to `C`. The candidate bundle becomes current. The guard is invalidated. The rename list is cleared. Gate opens. |

`failed` is not a phase. It is `idle` plus a sticky error in the status.

## 3. The table

Columns: **idle**; **A** = `syncing`, `validating`, `squashing` (locked, before the build); **W** = `waiting`; **B** = `building`; **P** = `pushing`, `finishing` (locked, after the build). A cell says what happens, which answer goes out and where the phase goes next.

| Event | idle | A | W | B | P |
|---|---|---|---|---|---|
| **Save** (`PUT /api/changes`) | Normal save. | `409 publish-in-progress`. Nothing written. | same | same (this is the cell design 1 flips) | same |
| **Poll tick** | Sync as in 2.10g. | Skipped. No back-off change. | Skipped | Skipped | Skipped |
| **Publish click** | Start: `status.publish` = `publishing`, phase `syncing`. | `409 publish-in-progress` | same | same | same |
| **Media upload** (`POST /api/media`) | Accepted (staging is outside `cms/work`). | Accepted | Accepted | Accepted | Accepted |
| **Reads** (`GET`s, status, overlay) | Answered | Answered | Answered | Answered | Answered |
| **Nothing to publish** (after sync) | n/a | `200 { commit: null }`. `cms/work` moves to the base. Phase `idle`. | n/a | n/a | n/a |
| **Wait for a running build times out** | n/a | n/a | `503 build-in-progress`. Phase `idle`. Nothing changed. | n/a | n/a |
| **Node unreachable** (validate) | n/a | `503 preview-unavailable`. Phase `idle`. | n/a | n/a | n/a |
| **Validation fails** (`422`, `409 referenced-by`) | n/a | The answer goes out. Phase `idle`. | n/a | n/a | n/a |
| **Build passed** | n/a | n/a | n/a | Phase `pushing`: take the lock, check `S`. The bundle does not change yet. | n/a |
| **Build failed or timed out** | n/a | n/a | n/a | `424 build-failed` with `firstError`. Nothing pushed. `cms/work` untouched. Candidate dropped. Log in `.cms/<site>/logs/`. Status `failed` (D-e). | n/a |
| **Push accepted** | n/a | n/a | n/a | n/a | Phase `finishing`, then `200 { commit, overwritten, renamed }`. Gate opens. If no build ran, the 2.10d rebuild of the published commit is asked for here. |
| **Push rejected: remote moved** | n/a | n/a | n/a | n/a | **A build ran for `C`:** `409 remote-moved`. Nothing pushed, `cms/work` untouched, candidate dropped, phase `idle` (D-c). **No build ran:** as in 2.10d, sync and push again, up to 3 retries. |
| **Remote moved with content** (seen by a retry's sync, no build ran) | n/a | n/a | n/a | n/a | The retry continues. The changeset is read again. `auto` is decided again. |
| **Remote moved with code** (seen by a retry's sync) | n/a | n/a | n/a | n/a | Nothing pushed. `503 build-in-progress` (builder on) or `503 upstream-changed` (`--bundle`). |
| **Retries run out** | n/a | n/a | n/a | n/a | `502 push-rejected`. Status `failed`. |
| **Push refused for another reason** (auth, hook) | n/a | n/a | n/a | n/a | `502 push-failed`. Status `failed`. |
| **Lock timeout** (30 s) | n/a | `503 busy`. Phase `idle`. | n/a | at the next lock: `503 busy`, candidate dropped, phase `idle` | `503 busy`. Phase `idle`. Nothing pushed. |
| **Server stops or crashes** | Nothing to lose. | Nothing remote. `C` is unreferenced and the next `git gc` takes it. | same | The candidate worktree stays on disk. The start-up sweep removes it. `cms/work` is at `S`, so no save is lost. | **After the push, before `finishing`:** the remote has `C`, `cms/work` is at `S`. The first sync after the restart finds the same content on both and a changeset with nothing in it. This cell needs its own test (invariant 5). |

Phase after every answer is `idle`; the status shows `failed` (with the message) after `424`, `502` and `500`, and `idle` after every other answer. Where the plan says `failed`, it is sticky until the next publish or save.

## 4. Invariants (the event-order test checks them after every step)

1. A save that answered `200` is in `cms/work` or in a pushed commit, never in neither.
2. When a build ran, the commit pushed is the commit that was built.
3. The bundle that serves is never ahead of what was pushed. It may be behind: a save is served by the overlay until the rebuild.
4. At most one publish runs.
5. No document is published twice as a change.
6. (new, phase 2 only) From the squash until the push, `cms/work` HEAD is `S`: nothing moves it. This is the assertion that design 1 removes, and it is the only invariant that changes then.

## 5. The event-order test

- Git, the build and the clock are injected, as planned.
- The events: save, poll tick, publish click, build passed, build failed, push accepted, push rejected (remote moved, with content), lock timeout, stop and restart.
- **Curated scenarios (the common and the critical ones), each run through the real functions with the invariants checked after every step:**
  1. The happy path, with a build and without one (`never`, or an `auto` that skips it).
  2. A save in each phase group (A, W, B, P): `409 publish-in-progress`, nothing written, and a save works again after the answer.
  3. A poll tick in each phase group: skipped, `cms/work` unchanged.
  4. A second publish click while one runs.
  5. A failed build: `424`, `cms/work` and the bundle untouched, the next save and publish work.
  6. A push race after a build: `409 remote-moved`, nothing pushed, and a second publish succeeds.
  7. A push race with no build: the retry, with content and with code.
  8. A lock timeout at the start and at the push after a build.
  9. A stop during the build, and a stop after the push before `finishing`, then a restart: a changeset with nothing in it, no document published twice.
  10. A validation failure, an unreachable node and "nothing to publish": the gate reopens each time.
  11. Publish, save, publish again: the second sends only the new save.
- **Seeded random on top:** a few hundred sequences of 8 to 12 events drawn from the event list above, with fixed seeds in CI and the seed printed on failure. A failure found by a seed becomes a curated scenario.
- Total under about 10 s. No new dependency.

## 6. Decisions for you (the cells where the answer is a real choice)

| # | Decision | Recommended | The alternative, and what it costs |
|---|---|---|---|
| D-a | **Saves are refused from the publish click to its end**, not only during the build | Yes | Refuse only from the squash: simpler for the user during `syncing` and `waiting` (up to about 2 minutes), but a save in the gap starts a rebuild and the publish answers `503 build-in-progress`, which is today's loop |
| D-b | **Which code a refused save answers** | Reuse `409 publish-in-progress` (already in the contract). 2.11d adds one message for it | A new `503` code: one more code and one more message for the same condition |
| D-c | **A push race after a build** | `409 remote-moved`, nothing pushed, the user publishes again | Retry automatically with a rebuild, up to 3 times: hides the race but costs minutes, and a retry builds code nobody asked to build |
| D-d | **The poll during a publish** | Skip the tick | Let it sync and treat a moved remote as a race: `cms/work` would move under a candidate, which breaks invariant 6 |
| D-e | **Status after `424 build-failed`** | `failed` with the message, so a reload still shows it | `idle`: the answer carries the error, but it is lost on reload |
| D-f | **Memory** | The candidate build uses the preview builder's one build slot. The builder's own triggers wait until it ends | Build in parallel: faster, but two Astro builds on a machine where `cms-server` alone is 128 MB at rest |

Other notes for 2.10e:

- The editor (2.11d) disables Save while `status.publish.state` is `publishing` and keeps the drafts, so a user rarely sees the `409`. The message exists for the second tab and for the race.
- `PublishAnswer` moves into `cms-contract` in this task (open from 2.14d).
- Under `never`, or an `auto` that skips the build, there is no `building` phase, no candidate and no change in the bundle swap: the flow is 2.10d's plus the gate.
